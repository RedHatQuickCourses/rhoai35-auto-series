In this section, we'll look at governance for MLflow at scale: how workspaces isolate and share prompts, and why a clear audit lineage is essential once you're running in an enterprise. The goal is simple to state. The right people have access to the right resources, every interaction is tracked, and if a compliance officer asks months later what generated a particular response, you have a definitive, documented answer.

Let's start with how MLflow organizes work, through workspaces. In OpenShift AI, workspaces map one-to-one with your OpenShift project namespaces. So all your experiments, runs, and registered prompts live inside that one boundary. Access is handled by standard Kubernetes Role-Based Access Control, or RBAC. If those terms are new, picture a namespace as a secure, walled-off area for your project, and RBAC as the rulebook for who's allowed in. As a practitioner, you don't set this up yourself; you inherit the isolation already configured for your project.

Isolation is great for day-to-day work, but some prompts need to be shared across the whole organization, say a security-vetted system instruction every team should build on. For that, cluster administrators can designate certain namespaces as Global Prompt Registry Namespaces. Other teams can then be granted read-only or edit access, which gives you a central, trusted library of enterprise-approved prompts.

If you're a cluster administrator, setting up a shared registry takes three steps. One, add the namespace to the global MLflow namespaces field in the dashboard config, or pick it directly in the dashboard settings. Two, label the namespace with the oc label command to mark it as a shared workspace. Three, make sure an MLflow instance is actually running in that namespace, because the operator needs an active server pod to create the role bindings. Once that's in place, other teams can view those prompts and use Save As to copy them into their own projects to iterate on.

Beyond organization, governance needs a complete audit lineage. For every inference, MLflow can automatically log the exact prompt string, the input variables, the model ID, the generation settings, the evaluation scores, and the final output. That audit trail matters for three reasons. First, reproducibility: you can recreate any past result. Second, rollbacks: if a production response regresses, you can trace it to a specific prompt version and revert to a known good state, with full evidence. And third, compliance: your risk and audit teams get the data they need to satisfy regulators.

Governance also covers the promotion process itself. Moving a production alias is powerful, but if you promote a version that performs badly, you ship a regression to everyone at once. The fix is to put a gate in front of the alias. That gate has two parts. First, automated evaluation through EvalHub, which runs candidate versions against standardized quality benchmarks and safety scans, and only lets promotion through if the scores clear your thresholds. Second, EvalCards, which are structured, versioned records of every test, stored as an MLflow artifact right next to your prompt.

You can move aliases by hand while you're experimenting, but production assets really benefit from a GitOps approach. Treat prompts and their evaluation configs as code, and you can manage them with tools like Argo CD or Flux. Now a pull request can kick off a pipeline that evaluates the prompt, generates an EvalCard, and promotes the alias only if every check passes. You don't have to build all of this on day one, but the system is designed to grow with you.

One last thing worth noting: this is the same MLflow platform you use for your predictive models. One unified platform means your team isn't juggling separate tools for predictive machine learning and generative AI.
