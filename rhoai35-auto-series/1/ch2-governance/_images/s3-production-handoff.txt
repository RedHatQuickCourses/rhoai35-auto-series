Welcome to this module on transitioning from a model winner to a live production endpoint. In this lesson, we will follow the repeatable path that promotes a validated model from a completed run to a live serving endpoint.

Once you have identified a model you trust, Red Hat OpenShift AI—or RHOAI—provides a short, repeatable path to get it serving real traffic, and the best part is that none of this requires cluster-admin skills. There are three primary ways to handle a completed run, and each serves a different purpose.

First, let’s look at how to export the notebook. This option is designed for tinkerers. When you click "Save notebook," AutoML generates a Python Jupyter notebook with the code pre-written to connect to your S3 storage, load the trained predictor, and execute batch scoring or custom validation. You should choose this path when you want to explore the model yourself, perform offline batch scoring, or provide a data scientist with a head start. Think of this as the "show me the code" door.

Next, you can register the model. This is the choice for governance. Selecting "Register" promotes the winning model version directly into the RHOAI Model Registry. You can think of the registry as your system of record; it versions your models, stores their metadata, and provides your team with a single, trusted place to determine exactly which model is running and its origin. A useful tip for those shipping a model for the first time: register it even if you are eager to deploy. The registry is what makes a model governable, versioned, discoverable, and auditable, rather than just a mystery file deployed on a whim.

Third, you can deploy to a serving endpoint. This is the path for production. This process turns a file into a live service. RHOAI deploys the model using the AutoGluon ServingRuntime for KServe, which instantly sets up a scalable REST API. Your applications can then retrieve predictions by sending a POST request to a standard KServe version two inference endpoint. Any service capable of making an HTTP request—such as a web app, a batch job, or another microservice—can now receive live predictions without needing to know how the model was built.

If terms like "KServe" or "serving runtime" are new to you, here is the short version: KServe is the component of OpenShift AI that runs your model as a web service and scales it for you. The AutoGluon ServingRuntime is a prebuilt engine that already knows how to load and serve AutoML models, which means you do not have to assemble any of the technical plumbing yourself.

When you look at the full arc of this process, you can see the path you have traced: you started with raw data in S3, moved through an AutoML run to a leaderboard and evaluation report card, proceeded to the registry, and finally arrived at a KServe REST endpoint. Raw data went in one end, and a governed, validated, production-ready prediction service came out the other in a matter of hours, all without you ever needing to touch the cluster.
