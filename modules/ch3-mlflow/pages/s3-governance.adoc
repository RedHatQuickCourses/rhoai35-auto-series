= Governance at Scale: Workspaces, Lineage, and Audit

Objective::

Explain how MLflow workspaces isolate and share prompts, and why the resulting audit lineage matters to the enterprise.

---

Making sure the right people can reach the right prompts, that nothing important is ever untracked, and that when someone in risk or compliance asks "what generated this answer six months ago?", you have a real answer.

== Workspaces: one per project

MLflow organizes work into *workspaces*, and RHOAI maps them cleanly to something you already know: an OpenShift project namespace corresponds *1:1* to an MLflow workspace. Your project's experiments, runs, and registered prompts all live inside that boundary, and access is controlled by the same Kubernetes RBAC that governs the rest of the platform.

NOTE: If "namespace" and "RBAC" are new terms, the short version is: a namespace is a walled-off area for one project's work, and RBAC is the rulebook for who's allowed in. You don't set this up yourself as a practitioner, you inherit the isolation your project already has.

== Global registries

Isolation is great for day-to-day work, but some prompts deserve to be shared across the whole company, think a security-vetted system instruction that every team should build on. For that, a cluster administrator can designate certain namespaces as *global* prompt registries, granting other teams either read-only or edit access.

The result is a central, trusted library of enterprise prompts: individual teams iterate in their own workspaces, while the organization maintains a shared shelf of approved instructions nobody has to reinvent.

.Designating a global registry (admin)
[NOTE]
====
Setting up a shared registry takes three steps, all performed by a cluster administrator:

. Add the namespace to `spec.globalMLflowNamespaces` in the `OdhDashboardConfig` (this field sits directly under `spec`, *not* under `spec.dashboardConfig`), or select it under *Settings -> General settings -> Global project* in the dashboard.
. Label the namespace so the platform treats it as a shared workspace:
+
[source,bash]
----
oc label namespace global-prompt-workspace opendatahub.io/global-mlflow-workspace=mlflow
----
. Make sure an MLflow instance is running in that namespace. The operator only creates the shared `odh-group-mlflow-view` role bindings once an active MLflow server pod is present.

Once that's in place, other teams see these prompts read-only and can use *Save As* to copy one into their own project before editing.
====

== Complete audit lineage

For every inference, MLflow can log the exact prompt string, the input variables, the model ID, the generation settings, any evaluation scores, and the output that was produced.

That lineage buys you three things practitioners and their organizations genuinely need:

* *Reproducibility.* You can recreate any past result because you know precisely what produced it.
* *Rollback.* When a production response regresses, you trace it to a specific prompt version and revert the alias, now with the evidence to justify it.
* *Compliance.* Risk and audit teams can prove which prompt, model, and parameters generated any historical response, which is often a requirement in regulated industries.

== The promotion gate: don't move an alias on a hunch

Promotion is powerful in both directions. Move the `production` alias to a new version and every application picks it up instantly, but if that version is worse than the last one, you've just shipped a regression to everyone at once. 

The governed answer is to put a *gate* in front of the alias: an automated check a candidate version must pass before it's allowed to become `production`.

* *Automated evaluation with EvalHub.* Instead of judging a prompt by hand, EvalHub runs a candidate version against a standardized suite of quality benchmarks and safety scans (and, for prompts that call tools, generated tool-call checks) and scores it. Promotion only proceeds if the scores clear the thresholds you set.
* *A paper trail with EvalCards.* Each evaluation produces an *EvalCard*: a structured, versioned record of what was tested and how the version scored, stored as an MLflow artifact right next to the prompt. That completes the compliance story from above, you don't just know which prompt version served a response, you can show the evidence that it passed your quality bar before it went live.


== Automating the gate with GitOps

Clicking to move an alias is fine while you're experimenting. Once prompts are production assets, teams usually want the discipline they already apply to code: changes proposed as pull requests, reviewed, tested, and promoted automatically, with nothing moving by hand.

Prompts, their evaluation configs, and their pipeline definitions are all declarative resources, so they can live in Git next to your application manifests and be reconciled by the same GitOps tooling (Argo CD or Flux) your platform team already runs. A pull request that edits a prompt can then kick off a pipeline that runs the EvalHub evaluation, generates the EvalCard, and moves the MLflow alias only if the checks pass. The promotion gate stops being something a person remembers to do and becomes something the system enforces on every change.

NOTE: You don't have to build this on day one. Nothing about the registry locks you out of it: the same aliases and versions you drive by hand in the dashboard are the ones a pipeline can drive automatically when you're ready.

== One platform for models and prompts

Here's a detail that's easy to undervalue: this is the *same* MLflow that tracked your AutoML accuracy scores in chapter 2. The instance versioning your predictive models also versions your prompt templates and traces your LLM calls. Your team doesn't juggle one tool for predictive ML and a separate one for GenAI, it's one governed platform across both.

== Where this leaves you

You can take raw tabular data all the way to a served predictive model (chapters 1 and 2), and you can take a raw idea for a prompt all the way to a versioned, governed, auditable instruction bound to a model (this chapter).

But a well-governed prompt still only knows what the model already knows. The moment you need it grounded in *your* proprietary documents, prompt engineering hits a ceiling. That's where the next chapter picks up: *AutoRAG*, which automates the retrieval pipeline that feeds your governed prompts the right context.
