In this module, we will explore the Prompt Management feature within Red Hat OpenShift AI. By the end of this section, you will understand why prompts require version control and how to use the MLflow-powered registry to version, alias, and bind your prompts to specific model configurations.

### Understanding Prompt Management

It is a common mistake to treat a prompt like a temporary text string—something to be copied, pasted, and tweaked indefinitely. However, a prompt is effectively a parameter that influences your application’s behavior just as much as your source code. When production results begin to regress, it is often impossible to track down which version of a prompt caused the issue.

Prompt Management—found in the dashboard under **GenAI Studio** and then **Prompts**—solves this by providing a central repository for your prompts. Powered by the MLflow prompt registry, it allows you to create, version, tag, and reuse prompt templates across your organization. It is important to note that while you may hear the terms "Prompt Management" and "MLflow prompt registry" used interchangeably, they refer to the same capability.

### Versioning, the Git Way

The registry functions similarly to a version control system for your instructions. Every time you register a change, the system saves a new numbered version, such as version one or version two, accompanied by a commit message.

There are two critical aspects of this system that ensure trustworthiness:
First, versions are immutable. Once a version is saved, it never changes. If you need to update a prompt, you must create a new version. This guarantee makes your results reproducible.
Second, you can compare versions side-by-side. The dashboard highlights differences between versions, allowing you to see exactly how your wording has evolved over time.

### Using Aliases for Deployment

To prevent version numbers from cluttering your application code, we use aliases. An alias is a movable label that points to a specific version. For example, you might have a "production" alias pointing to version two, while a "latest" alias automatically tracks the most recent version.

Your application references the prompt by its alias rather than its version number. This means that when you are ready to promote version three to production, you simply update the "production" alias to point to the new version. There is no need for code changes or redeployments. If you ever need to revert to a previous state, you can perform a one-click rollback by simply moving the alias back.

Before promoting an alias, we highly recommend using the Playground’s "Compare" view. This allows you to load two different versions side-by-side, run the same input against both, and evaluate performance metrics like latency and token usage to ensure the new version is indeed an improvement.

### Prompt Settings and Templates

A prompt is more than just text. The registry stores a model configuration alongside each prompt, including the model name, temperature, and maximum token settings. This ensures that the entire "recipe"—including the specific tuning required for that prompt—is preserved. Furthermore, prompts can be bound to specific providers, such as Llama, Granite, or Claude, allowing teams to switch underlying models without rewriting their prompt code.

If your prompt requires flexibility, use placeholders like double-curly-braces. You only need to register the reusable shape of the prompt once. When you load a templated prompt into the Playground, the interface automatically detects these placeholders and provides input fields, allowing you to define the runtime values before you run your test.

### Beyond the Prompt: Playground Agents

While the registry captures the prompt and its settings, complex experiments often involve additional components like RAG knowledge sources and connected tools. To capture this entire execution recipe, you can save your session as a "Playground Agent."

When a teammate opens a saved agent, they don’t just get the prompt and temperature; they receive the exact model runtime, the same vector store, and the same tool definitions you used. This provides true, session-level reproducibility.

*Note for administrators:* Playground Agents are currently a Developer Preview feature and are disabled by default. They can be enabled by setting the `agentConfigManagement` feature flag to `true` within your `OdhDashboardConfig`. Once enabled, these agents are stored as Kubernetes resources within your project namespace, enabling easy collaboration across your team.
