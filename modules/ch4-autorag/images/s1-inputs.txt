In this section, we'll prepare the two inputs every Auto RAG run depends on: your document corpus, and a ground-truth evaluation dataset. Get these two right, and you've laid the foundation for an accurate retrieval run.

Let's start with the document corpus, the knowledge base you want the model grounded in. A few practical rules about your files. Auto RAG supports several common formats, including PDF, DOCX, PPTX, Markdown, HTML, and plain text. You can host them in an S3-compatible bucket, or upload them directly through the user interface.

On file size: if you upload through the interface, there's a limit of 32 megabytes per file. If you point Auto RAG at a folder in S3-compatible object storage, there's no per-file limit, though a run will automatically sample up to one gigabyte of documents in total.

A tip for your first time: start small and keep your files clean. A handful of high-quality, text-based documents will teach you more about how Auto RAG behaves than one giant, messy archive. You can always scale up once you're comfortable.

One caveat for the Technology Preview: Auto RAG doesn't run optical character recognition on image-only PDFs, and it can't pull text out of embedded images. So if your PDFs are scanned pages, that text won't be retrievable. Table structure extraction is available, but only when you choose the Better Quality run preset.

Now the second input: the evaluation dataset, your answer key. This is the most important piece, because Auto RAG can't rank retrieval patterns without knowing what a correct answer looks like. You provide the answer key as a JSON file that pairs representative questions with their known-good answers and the specific source documents where those answers live.

Each entry needs three fields. First, the question, a real inquiry a user might actually ask. Second, correct answers, a list of acceptable phrasings; giving a few variations means a good answer isn't marked wrong over minor differences in wording. Third, correct answer document IDs, which name the specific source documents that contain the answer. That third field is what lets Auto RAG score the quality of retrieval, not just the final text generation.

One important caution on those document IDs: use only the base filenames, like policies dot pdf. Never include a folder path. That's a common mistake, and it causes errors on the very first run.

To make this easier, OpenShift AI 3.5 added an inline evaluation-file creator. You type a question, its answer, and the source document straight into the interface. That's the fastest way to get started with a few test cases, but for a comprehensive evaluation you'll still want a full JSON file with a wide range of questions that reflect what your users will really ask.

With your documents and your answer key ready, Auto RAG has everything it needs to begin. In the next section, we'll look at the search space it explores on your behalf, and, just as importantly, how to read the scores it reports back.
